# 启动组合：功能评估与实施方案

启动组合自 v0.11.0 起提供。首版通过自动检查、组件拖动、真实软件和本机 helper 的真实 UAC 专项，适用范围见实施记录。首轮设计始于 2026-11-16，基线为 `main` / `63763d3`（v0.10.0 发布记录）。

## 1. 建议与价值判断

**建议做，作为 Rust 主线的独立小功能，先验证运行识别，再交付“启动组合”首版。** 目标是把固定的一组应用变成一个可搜索入口：输入“开黑”，选中组合，按 Enter，补齐游戏、语音和加速器。

它与 Velo 的“快速找到并打开应用”定位直接相关。反复使用 2–5 个应用的场景最有价值，例如开黑、办公、开发、直播；三款应用从三次搜索和确认变为一次，省去两轮操作。这是操作数分析，不是实测耗时或用户需求统计。

目前只有本次明确需求，没有采用率或用户调研，不能据此判断它应优先于现有缺陷修复。建议先用“开黑”及另一个日常场景试用一周：是否反复使用、配置是否容易、是否真的减少重复操作，以及有无误跳过或重复启动，再决定是否扩展。

价值的前提是运行识别足够可靠。**“批量发起启动”较简单，“知道哪个应用已运行”是主要成本和上线门槛。** 首版应明确支持范围，不能承诺所有 Windows 应用都能自动识别。

### 取舍

- 手动逐个打开：没有新增维护成本，但固定场景仍需反复操作。
- 批处理或快捷方式：适合一次性的个人方案；运行识别、路径维护、参数、失败反馈需要自行处理，不易形成 Velo 内可管理的体验。
- Velo 原生启动组合：复用应用库、搜索、Shell 启动和原子存储，符合现有产品路线；新增复杂度集中在运行识别和批次状态，推荐采用。
- 通用工作流引擎：涉及步骤依赖、脚本、条件和恢复，超出本次收益，暂不纳入。

重构计划曾将组合启动排除在迁移范围之外；最新主线已发布 Rust v0.10.0。本需求作为用户明确提出的独立新增功能评审，不回写或扩大历史阶段验收结论，不再为 Go/Wails 实现一份功能。

## 2. 用户体验与首版范围

### 创建和管理

建议在设置中增加“启动组合”管理入口，支持创建、修改、删除。

1. 点击“新建组合”，输入名称“开黑”。常规配置只需名称和应用两项，别名放在可选项中。
2. 左侧搜索已有应用，拖到右侧成员区域；点击“添加”提供等价的键盘/鼠标回退。支持连续添加，不要求每加一项重新打开选择器。
3. 应用库展示应用图标，支持搜索和滚动；重复拖入只保留一份，不执行任何程序。添加按钮使用居中的“＋”图标。库外程序先通过已有“自定义应用”添加，再选择组合成员。
4. 点击“保存”。默认自动处理运行检测，普通用户无需填写路径、进程名、参数或 PID。只有游戏启动器、身份歧义等异常成员才显示“需要设置运行检测”，提供选择实际主程序的修复入口。

编辑器采用“应用来源 → 组合成员”的双区布局，右侧有明确的投放提示与移除按钮；拖动来源条目到成员区即完成添加，拖出不代表删除，避免误操作。成员顺序不表达等待依赖。空组合也允许先编辑，但不足两个成员不能保存。取消和返回丢弃未保存草稿时提示，失焦/隐藏则保留草稿；运行检测的迟到结果不得混入另一个组合。

组合成员统一引用已有应用 ID；其失效时提供重新选择，不静默回退旧路径。配置只在 Velo 内部的应用库和成员区之间完成，保存只提交一个组合文件，取消不会改变全局应用库或首页固定。

本次按用户澄清取消组合页的资源管理器拖文件、文件批量导入和“选择文件”添加入口。运行检测的特殊修复仍可选择实际主程序，这不会增加组合成员。内部拖动不涉及资源管理器与管理员窗口之间的拖放权限边界。

首版建议上限为 50 个组合、每组 2–20 个成员、名称 1–32 个字符。这些是防止误操作和无界任务的设计上限，尚未做性能验证。组内相同应用 ID 不重复添加；同一运行程序的不同入口提示合并或确认其语义，不静默丢弃成员。组合名称和别名按统一归一化规则检查，阻止组合之间的重复入口。

### 搜索与执行

搜索“开黑”显示一个带独立类型标识的结果：**开黑 · 启动组合**，副标题为“游戏、语音、加速器 · 3 个应用”。输入过程中不查询进程或磁盘，只在执行后检查运行状态。

按 Enter 执行；Space 沿用现有 `space_launch` 设置，IME 合成期间继续优先交给输入法。输入文字本身不会自动执行。精确匹配组合优先于模糊匹配的应用；与应用同名时同时展示、明确标识，精确程度相同则保留应用在前的稳定顺序。普通应用之间的搜索排序保持原有契约。创建时提示同名冲突，用户可修改名称或通过别名区分，不增加命令解析语法。

“同时启动”定义为**一次操作后并发发出各成员的启动请求，不等待前一个应用加载完成**，不保证窗口在同一时刻出现。建议最多 3 个 Shell 工作槽；其余在本批次内等待空位。成员排列只影响展示和派发优先级，不表示依赖关系。

首版交付创建/编辑/删除、名称及别名搜索、运行检查、防重复触发、逐项结果和失败重试。组合固定到首页、组合常用排序可在后续补充，避免首版同时改动首页固定数据与导航。

### 执行结果

- 全部未运行：发出 3 个启动请求。
- 语音已运行：跳过语音，发出游戏和加速器的启动请求；不激活或抢占已有语音窗口。
- 全部已运行：提示“3 个应用均已运行”，不再调用 Shell。
- 一项失效：该项提示“已移动或删除，请重新选择”，其他项继续。
- 一项状态无法确认：该项暂停自动启动，其他项继续；结果中提供“重新检查”和明确的“仍然打开”。后者是用户对本次成员的主动操作，不改变默认规则。
- Shell 接受请求：显示“已发送启动请求”；不能将其写成“应用已就绪”。
- 某项启动失败：显示具体原因，只重试失败或待确认项；重试前重新检查进程。

任务接受后沿用当前清空输入和隐藏启动器的行为；最近一次组合结果保留在会话内，再次呼出可查看详情及取消未派发成员。部分失败不自动抢回焦点；全部失败时，只有生命周期 generation 仍匹配才恢复窗口。全部已运行也保持不抢焦点，并在下次呼出显示结果。

“加速器启动”只表示程序被打开，不代表已登录、完成加速或游戏可以联网。需要“先加速成功再打开游戏”的场景属于后续依赖编排，首版不作此承诺。

## 3. 如何判断“已经启动”

### 默认规则

**同一 Windows 用户、同一交互会话中，存在与成员主程序对应的进程，就视为已运行。** 托盘驻留和没有主窗口的进程也算运行。不以窗口标题、是否在前台、单独的进程文件名或历史启动记录判断。

在 Windows 原生层按需取得进程快照，通过受限查询权限读取候选进程映像路径，完成路径规范化后比较。可先用进程文件名缩小候选，但最终必须比较完整程序路径；当前用户和会话也要校验。路径存在大小写、长短路径、链接或重解析点歧义时，补充文件身份校验或返回“无法确认”，不能仅将字符串转小写后当成完整方案。

使用三态结果：`Running`、`NotRunning`、`Unknown`。只有相关候选进程检查完整且未匹配时才能返回 `NotRunning`；相关进程权限不足、枚举失败、身份无法判定或存在歧义时返回 `Unknown`。其他无关进程的访问失败不应使所有成员都变成未知。查询期间正常退出的进程按瞬时变化处理。

### 各类目标的边界

- **直接 `.exe`**：默认以其完整可执行文件身份匹配，是首版主要支持对象。
- **可解析为 `.exe` 的 `.lnk`**：使用解析后的主程序做运行判断，启动仍执行原快捷方式，保留现有参数、工作目录与 Windows 行为。
- **Steam 等游戏启动器**：启动入口和运行标识必须分开。`steam.exe` 已运行不能证明指定游戏已运行；需要用户选择游戏的实际主程序。后台代理、更新器、反作弊程序不能自动当作游戏本体。
- **带参数的入口**：应用 ID 包含参数，而进程路径通常无法证明参数和 profile。普通“同一程序只打开一次”的入口可由用户确认按程序去重；同一宿主承载多个游戏、浏览器 profile 或不同任务时必须单独配置运行程序，否则标记“需确认”，不能按宿主进程自动跳过。
- **Windows Apps / AUMID、协议、脚本和通用宿主**：首版不提供自动运行识别，管理界面说明原因，不把 `explorer.exe`、`cmd.exe` 等宿主当作应用身份。系统快捷、电源操作、目录和嵌套组合不允许作为首版成员。
- **管理员或受保护进程**：尽可能通过有限查询确认；仍无权限时返回未知，Velo 不为检查进程自动提升权限。

“指定运行程序”通过选择实际 `.exe` 配置，不要求普通用户输入进程名、PID、正则或脚本。配置时显示“启动入口”和“检测运行程序”供核对；共享一个运行程序的不同成员必须提示冲突。

### 防止连续触发与竞态

进程检查与启动之间不存在跨应用的原子事务。外部程序恰好启动、快速退出、游戏启动器派生子进程等情况，无法由 Velo 彻底消除竞态，应用自身的单实例机制仍是最终保障。

Velo 内部需做到：

1. 一次只接受一个启动操作批次；执行中重复触发返回当前进度，不再排队。既有单应用启动入口也经过这一调度边界。
2. 派发前占用规范化的运行标识，组内共享标识只派发一次，并在派发前复查相关进程，缩小快照过期窗口。
3. Shell 返回后保留短期“已派发、待观察”的标记，避免进程尚未出现时再次触发产生重复请求。建议先以 15 秒为观察窗口候选值，通过真实慢启动样本调整。
4. 下一次触发时按需检查：已观察到进程则按已运行跳过；观察窗口内尚未出现则提示“启动中”；超时仍未观察到则提示“启动结果未确认”，由用户重新检查或主动重试，不能仅因超时自动再开一次。

不增加常驻进程轮询、WMI 订阅或持续计时扫描。上述防重状态仅在本次 Velo 会话内有效，重启后通过实际进程重新判断。

## 4. 与当前 Rust 架构的衔接

### 已有能力与必须改动的约束

现有 `core/launch.rs` 负责构造启动命令，`platform/windows/launch.rs` 使用 `ShellExecuteExW`，`core/service.rs` 通过容量 1 的队列和 `action_busy` 处理单项启动及写入，`business.rs` 与生命周期模块负责输入、显隐和失败恢复，可以复用这些边界。

不能简单循环调用现有 `Runtime::launch`：忙碌标志会拒绝后续项。现有 `Shared::event` 还会按事件类型合并通知，如果每个成员都发出独立 `Launched`，可能丢失结果；现有完成事件又会释放忙碌状态。这些约束需作为批次改造一起处理。

### 建议组织

- 新增 `core/launch_groups.rs`：组合定义、引用校验、运行结果三态的决策、执行计划、成员状态与批次汇总；核心规则不持有 Win32 句柄。
- 新增 `platform/windows/processes.rs`：进程快照、用户/会话校验、程序身份解析；Win32 句柄用 RAII 释放，FFI 边界给出必要的 SAFETY 注释。
- 扩展 `core/service.rs`：接收类型明确的单应用/组合请求，生成 `run_id`，安排有界任务、汇总结果、串行提交历史。此处只承担协调；不把整套组合规则堆入服务或 `main.rs`。
- 搜索层增加独立的组合索引与有类型的候选项，例如 `Application` / `SystemTool` / `LaunchGroup`；复用现有归一化和匹配规则，不能伪造 `AppItem.path` 为可执行的组合命令。
- `business.rs`、`ui.rs` 与 `ui/` 接入管理页面、搜索类型和结果展示；UI 回调只投递命令，进程查询、快捷方式解析和写盘全部在后台。

最多 3 个 Shell 工作槽仅在有批次时工作，每个线程创建并释放自己的 COM STA；不跨线程传递 COM 对象，不为每个成员创建无界线程。优先复用既有模块和标准库，实现小型固定调度，暂不引入异步运行时或通用工作流框架。调度和存储协调不能在 UI 线程等待 Shell 或持锁执行 Shell。

批次状态采用一个带 `run_id` 的完整有界结果快照，至少包含 `Queued`、`Checking`、`Launching`、`Submitted`、`AlreadyRunning`、`NeedsReview`、`Failed`、`Cancelled`。进度通知可以合并，但合并后必须仍包含所有成员的最新状态；只在整个批次终态时释放启动忙碌状态。退出和窗口显隐的 generation 与任务身份分别校验，迟到事件不得恢复已隐藏窗口或重新插入已删除组合。

取消只阻止尚未派发的成员，不关闭已运行应用。普通启动继续保留系统正常的 UAC 行为；不提供“整个组合以管理员运行”。可识别的提权提示串行处理，UAC 取消只影响对应成员。原生同步 Shell 调用不能保证即时取消，退出需等待已进入调用返回，随后清理线程和 HWND 所有权；不能通过丢弃线程或强杀应用伪装为清理完成。这一边界需实机验收。

### 依赖与资源

优先只增加已有 `windows-sys` 的进程枚举 API feature（预计 `Win32_System_Diagnostics_ToolHelp`），复用现有 Threading、Security 和 FileSystem 能力，不升级工具链和锁定版本。MIT / Apache-2.0 依赖许可继续保留；若原生身份解析需要其他 feature，应在实现 PR 列明原因。

进程快照与路径校验按次执行，批次完成释放临时资源；搜索与隐藏空闲不产生持续查询。新增峰值内存、线程数、CPU 和启动延迟需要同机实测，本方案没有测量结果，不宣称资源开销为零或已满足预算。

## 5. 数据、历史与失败语义

建议单独保存 `%LOCALAPPDATA%\Velo\launch-groups.json`，不改变应用 ID 算法，也不升级既有 `application-library.json` 的格式。预览和测试继续使用独立实例及隔离数据目录。

每个组合保存稳定 ID、名称、别名和成员。成员记录现有 `app_id`、仅用于显示的名称，以及自动/指定主程序的运行规则，不另存启动入口。稳定组合 ID 一次生成并检查唯一性，不能由名称计算，重命名不换 ID。以下表达应用库引用成员的结构，尖括号是说明标记，不是实际可加载数据：

```json
{
  "version": 1,
  "groups": [
    {
      "id": "group:<稳定随机标识>",
      "name": "开黑",
      "aliases": ["游戏时间"],
      "members": [
        {
          "app_id": "<已有应用ID>",
          "display_name": "游戏软件",
          "running_rule": {
            "kind": "executable",
            "path": "C:\\SyntheticApps\\Game\\Game.exe"
          }
        },
        {
          "app_id": "<语音应用ID>",
          "display_name": "语音软件",
          "running_rule": { "kind": "auto" }
        },
        {
          "app_id": "<加速器应用ID>",
          "display_name": "加速器软件",
          "running_rule": { "kind": "auto" }
        }
      ]
    }
  ]
}
```

执行目标从当前可信应用快照按 ID 取得，不能把显示名称或备份的旧路径当作找不到成员后的执行回退。应用移动、更换参数导致引用 ID 改变时，保留组合引用，标记失效并要求重新选择；删除自定义项后，如果当前自动索引仍提供同一 ID，引用仍可使用，否则停用该成员。索引刷新不得静默删除组合成员。

首次没有组合文件时只表示“尚未配置”，无需启动时创建文件。有效数据读取不重写；保存保留根、组合、成员和规则的未知字段。损坏或未来版本保留原件，禁用组合读写并给出提示，普通应用搜索与启动继续工作；不通过空库覆盖恢复。

组合编辑复用同目录临时文件、flush、Windows 原子替换和串行提交机制，保存成功才发布快照。批次运行使用接受时的不可变定义；首版在执行期间拒绝组合编辑/删除，完成后可操作，晚到事件只能更新仍存在且身份匹配的会话结果，不能恢复已删除定义。

历史遵循以下规则：

- 成员只有 Shell 确认接受启动请求才增加原有启动次数；已运行跳过、未知、失败和取消不增加。
- 组合查询“开黑”不写入每个成员的查询学习，成员计数使用空查询，避免“开黑”以后把游戏、语音和加速器分别推到组合前面。
- 一批成员计数尽量合并为一次 `history.json` 原子提交，成功后只发布一次快照；首版不增加组合常用排序或新的跨文件统计事务。
- 历史写盘失败时真实启动无法撤销，明确提示“启动请求已发送，历史保存失败”，不能把它当成 Shell 失败而自动重试。
- 组合不是可回滚事务：某项失败不关闭已经打开的应用，不自动重启其他成员。

当前“设置备份”只备份 `config.json`；新组合文件不会自动进入该功能。首版更新数据目录/迁移文档，说明迁移组合需要一并保留 `launch-groups.json`，并核对安装、升级、原文恢复档案与卸载保留策略是否涵盖新文件。降级到旧版时保留此文件，恢复新版本后仍能读取；不把配置备份宣传成完整组合备份。

## 6. 分阶段落地与投入

粗估单人 **5–8 个开发日**，包含必要回归和当前可用 Windows 环境实测，不含不可用硬件、应用厂商适配或依赖编排。估算基于源码阅读；本轮基础模块和原生检查的实际进展见文末，目标软件和界面接线后应再次校正。

1. **识别验证，约 0.5–1 日。** 建立隔离 helper 和代表应用清单，验证完整路径、会话、快捷方式、管理员进程，以及游戏真实主程序的匹配。至少覆盖目标游戏、语音、加速器，记录自动支持/需要指定/不支持。如果核心场景无法可靠识别，先修订支持范围，不直接承诺完整功能。
2. **数据与执行内核，约 1.5–2 日。** 增加组合独立存储、三态判断、有界批次、派发防重、取消和合并历史；补充关键决策和失败测试，保持单应用行为回归通过。
3. **管理与搜索界面，约 1.5–2.5 日。** 实现多选、运行规则修复、搜索候选和最近结果；接入 IME、键盘导航、显隐 generation 与两种渲染器。
4. **实机验收与文档，约 1.5–2.5 日。** 验证核心三应用场景、权限和慢启动、部分失败、退出、升级/降级数据保留及资源范围。通过后再安排版本与发布，不预先改正式版本号。

每步可以形成独立、可评审的提交/PR；首版不同时添加延时启动、就绪探测、依赖 DAG、自动加速、开机自动执行、脚本、窗口布局、整组关闭、嵌套组合、云同步或插件。确有重复使用价值后，再按反馈选择下一项。

## 7. 验收条件

### 核心行为

- 三个成员均未运行时，各收到一次启动请求；语音已运行时只派发另外两项；全部已运行时零 Shell 调用。
- 两个不同目录中的同名程序不会互相导致跳过；托盘应用能识别，其他用户/会话中的进程不误判成本会话已运行。
- Steam 已启动、游戏未启动时不会跳过游戏；指定游戏主程序运行时能跳过；多参数宿主不能按一个宿主进程误跳过所有成员。
- 权限不足返回“需确认”，不伪造未运行；用户可重新检查或主动打开该成员。
- 快速连续触发、不同成员共享运行标识、进程延迟出现和执行中重试均不产生 Velo 内部的重复派发。
- 单项删除、UAC 取消、Shell 失败后其余项继续；只重试失败项并重新检测；历史失败不会触发重复启动。
- 不把已发送请求写成加载完成，不要求加速器就绪；不会关闭已有应用或激活被跳过的窗口。

### 数据与 UI

- 组合重命名 ID 不变，应用移动/刷新/删除显示失效引用，保存失败保留原文件和旧快照。
- 未知字段往返保留，损坏/未来版本原件不变且单应用仍可使用；无组合用户无需迁移现有应用库。
- 应用精确匹配、普通搜索排序、固定/常用、单应用启动与失败恢复通过既有回归；组合查询不污染成员查询历史。
- IME 合成、Enter/Space、列表与网格导航、设置草稿及失焦/再次呼出保持一致；部分失败不抢焦点，迟到事件不恢复已隐藏窗口。
- 批次状态不因同类型事件合并丢项，终态前不误解锁；取消、退出和原生弹窗清理有明确结果。

### 验证入口与证据

行为单测使用合成进程清单和可控 Shell 执行器，覆盖未知、竞态、防重、失败与历史提交边界。原生检查仅启动专用 helper；真实游戏/语音/加速器另做当前机器实测，不能用合成消息替代。

实现阶段按仓库入口执行：

```powershell
./scripts/verify-rust.ps1 -Product -SmokeTest
```

此入口从仓库根目录运行，包含固化兼容基线检查，不再运行旧 Go oracle。

两种渲染器均需完整检查和实际 UI 截图；Windows 10/11 在当前可用环境分别验证。记录基线与新构建身份、渲染器、进程规模、样本范围，以及隐藏空闲/触发时 CPU、PrivateBytes、线程/句柄和派发延迟。不把设计上限、估算工期或历史性能写成已验证结果。测试使用独立 `--instance-id` 与 `--data-dir`，必要时独立热键，完成后仅清理本次创建的 helper 和实例。

以上是完整功能的验收清单，不代表已经通过。本轮基础模块的实际实现与验证范围单独记录，不扩大成完整功能验收。

## 9. 实施进度与验证

按用户补充的简单拖放要求，先交付可独立验证的基础模块：

- `core/launch_groups.rs`：组合数据、50 组/每组 2–20 项校验、未知字段保留、原子保存复用；缺少文件时不创建，损坏或未来版本返回错误并保留原件。
- 同模块的编辑草稿：重复拖入去重，超限明确计数；切换组合、取消或移除成员会使旧检查票据失效；保存失败或迟到保存不误清除修改状态。
- 成员仅引用应用库；原资源管理器文件预处理与独立启动入口已按用户澄清移除。特殊成员的运行检测仍由后台检查所选 `.exe`。
- `platform/windows/processes.rs`：按需检查同用户、同会话的进程，使用卷序列号和 128 位文件 ID 区分同名程序并识别硬链接；权限或相关身份无法确认时返回未知，正常退出或已消失的 PID 不伪装为存活进程。

依赖只增加既有 `windows-sys 0.61.2` 的 `Win32_System_Diagnostics_ToolHelp` 和 `Win32_System_RemoteDesktop` features，分别用于原生枚举与会话检查，不新增 crate、不升级锁定版本，沿用 MIT / Apache-2.0 许可。进程检查没有常驻线程或计时扫描；实际资源与目标软件兼容性尚未测量。

已接入 Slint 组合管理页、带图标的应用库内部拖动、搜索候选、最多三个工作槽的原生启动、运行跳过/待确认防重、取消与重试、结果快照及一次合并历史写入。图标按可见范围加载并复用现有缓存；从设置进入组合后返回设置保留原草稿。

组件检查覆盖一次实际的 Slint 指针拖动、重复去重、保存提交和放弃/取消确认，并生成浅色/深色编辑及结果截图。隔离的原生测试只执行本项目 helper，已验证三成员中派发两项、跳过一项，再次触发零重复派发、历史只记录两项且查询学习为空；所有 helper 自行退出。
