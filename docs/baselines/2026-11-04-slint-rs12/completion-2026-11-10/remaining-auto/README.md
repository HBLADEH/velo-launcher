## 实际输入接收校准

新增的原生集成测试程序只在隔离 exe、PID/创建时间、唯一 HWND、实际前台及焦点都符合预期时发送固定 Unicode `a`，不运行选择项。隐藏窗口、外来窗口及 PID 创建时间不符会拒绝输入；桌面不处于默认可交互状态时拒绝操作。所有记录明确标注机器输入，不计物理 Alt+Space 样本，不改写已有人工输入证据。原产品日志不能识别所有外部注入来源，因此外部 `machine_input=true` 身份必须一并保留，不能只凭产品的 `synthetic=false` 改称物理输入。

探针提前就绪后启动原冻结程序，使用 QPC 与系统精确 FILETIME 的前后括号，将实际 OS 进程创建、热键派发与搜索框非合成编辑回调配对。区间内记录时钟映射波动，并附带声明的 0.1 ms guard；观察到跳变则拒绝时间结果。采用进程私有高精度等待器，目标间隔 2 ms，不改变全局 timer period；每次实际发送时间及最大间隔保留在 trace。记录的是可验证的接收上界，**不宣称数学意义上的首次可能就绪时刻或任意时钟跳变都已被物理仪器校准**。

为避免工具中途变化混算，最终统一为 build8，三候选各 3 次暖启动与 20 次热键均有效，无事件丢失，分别见 [Software](readiness/software.json)、[FemtoVG](readiness/femtovg.json)、[Wails](readiness/wails.json)及[同版本矩阵](readiness-matrix.json)：

- Software：暖启动范围 **161.321–251.649 ms**，中位数 **211.338 ms**；机器热键接收到字符上界 P95 **44.818 ms**。
- FemtoVG：暖启动范围 **548.660–619.388 ms**，中位数 **578.140 ms**；机器热键上界 P95 **26.741 ms**。
- Wails：暖启动范围 **739.964–867.768 ms**，中位数 **782.071 ms**；机器热键上界 P95 **36.871 ms**。WebView 使用正常退出的独立测试 profile 副本，未复制正式 profile。

上述 60 次机器热键的 P95 上界均低于 50 ms，支持本机这一机器集成校准条件；它们与此前至少二十次的真实热键/IME验收分开。暖启动表中的 500 ms 只是计划**冷启动**目标的参照线，不通过暖样本宣称冷预算达标。FemtoVG/Wails 的暖上界超出该线如实保留，不能仅凭上界认定它们此前绝不可能更早接收输入。每次三个暖样本仅观察，不扩大成稳定启动分布或跨机结论。

较早普通 `Sleep(2)` 实际调度可间隔约 10–15 ms，热键上界较高；引入私有高精度 timer 后另开新会话。早期工具、所有有效/无效结果的原始 report hash 和分组均在 [earlier-readiness-runs.json](earlier-readiness-runs.json)，不与最终 build8 混算，也不删除较慢样本以“达标”。

## 动画 CPU 与帧节奏

复用第四版 1000/10000 项实际图标夹具和原冻结产品，后台发现完成后每条件执行五次机器查询，查询前等待 700 ms 清空/稳定。20 ms 请求间隔记录根进程及所有观察到的后代，保存 PID/创建身份、CPU 原始累计计数和每次读取的 QPC 括号；Wails 包含 WebView 完整树，不把采集器 CPU 算进产品。500 ms 的查询+动画窗口用前后完整 CPU 样本保守包围，进程复用、计数下降或中间不可读则整轮无效。全部 30 次均通过身份与区间检查，见 [animation-matrix.json](animation-matrix.json)及逐条件报告。

各窗口整树 CPU 累计计数差的中位数如下，均以 **CPU 毫秒/500 ms 墙钟窗口**表示，包含查询、模型与绘制工作，不是纯 GPU 渲染时间：

- Software：1000 项 **46.875 ms**，10000 项 **125.000 ms**。
- FemtoVG：1000 项 **171.875 ms**，10000 项 **187.500 ms**。
- Wails：1000 项 **750.000 ms**，10000 项 **640.625 ms**；多进程、多线程累计可超过 500 ms。

本机 CPU 计数最小正步长约 **15.625 ms**。逐条件报告保留实际样本间隔、进程数、采集器 CPU 与读取开销，不能将总 CPU/变化状态的平均数写成精确逐帧 CPU。完整原始资源与帧文件留本地并保存 hash；桌面变化状态间隔的中位数约 16.6–16.7 ms，Software 部分间隔约 67–69 ms，原长间隔不剔除。Desktop Duplication 的合并帧与几何拒绝也保留，不把桌面变化节奏当作所有 GPU 指令耗时或没有漏帧的保证。

这补齐了重构计划要求的“动画期间另测 CPU/帧耗时”的有限本机观察。精确每帧 GPU 执行与屏幕像素发光时间并非原计划的必过指标；没有测得这些数值，不因此前检查点扩大了“待验”的措辞而虚构完成。高 DPI/其他驱动与更广查询性能范围仍不扩大。

## 焦点失败的复核

Wails 自动校准中保留了两次工具拒绝：旧 build4 在首个 probe 后检测到焦点条件消失，旧 build7 在轮询与实际发送前的二次检查之间条件变化，**还没有发送任何 probe**。后者保存了当时仍为目标前台的焦点交接事件。原程序都正常退出，未观察到崩溃；原始失败 trace 和 hash 见 [focus-review.json](focus-review.json)及 failures/，不会改标成功。

工具已将“目标内部焦点交接、先不发送并等待”与“前台离开目标进程、立即停止”分开，并记录发送前拒绝的 deferral；真实 `SendInput` 失败仍停止，不盲目重试。最终 build8 的九次暖启动和六十次机器热键全部通过，源文件和二进制身份另列，未修改 Velo 的正常失焦隐藏规则来使测试变绿。

这能解释新工具的拒绝边界，**不能解释原人工 Wails 闪现/不能输入或 `software-3` 最初失焦的确切原因**：旧日志没有保存前台赢家，无法倒补。真实热键、IME与新受控复测通过作为当前范围的回归证据，原用户报告、原失败及其原因未知仍保留；不写成产品故障已修复。
